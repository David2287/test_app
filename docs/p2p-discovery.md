# P2P Поиск пиров в локальных сетях

## Стратегия: двухрежимное обнаружение

Сетевое окружение непредсказуемо (открытые VLAN, управляемый WiFi, ad-hoc сети), поэтому мы используем два взаимодополняющих механизма обнаружения, работающих параллельно.

```
┌─────────────────────────────────────┐
│         Discovery Engine             │
│                                      │
│  ┌────────────────────────────────┐  │
│  │         mDNS (NSD)             │  │
│  │  - Тип службы: _p2pmsg._tcp    │  │
│  │  - Стандартный mDNS (RFC 6762) │  │
│  │  - Android NsdManager API      │  │
│  │  - Работает в большинстве      │  │
│  │    LAN/VLAN WiFi               │  │
│  └────────────────────────────────┘  │
│                                      │
│  ┌────────────────────────────────┐  │
│  │        UDP Heartbeat            │  │
│  │  - Броадкаст на порт 42000     │  │
│  │  - Полезная нагрузка: JSON     │  │
│  │  - Интервал: 5 секунд          │  │
│  │  - Запасной вариант, если      │  │
│  │    mDNS заблокирован           │  │
│  └────────────────────────────────┘  │
└─────────────────────────────────────┘
```

## mDNS / Android NSD

### Регистрация службы

Каждое устройство регистрирует службу при запуске:

| Поле            | Значение                   |
|-----------------|----------------------------|
| Service Type    | `_p2pmsg._tcp`             |
| Service Name    | `P2PMsg-<device_id>`       |
| Port            | Динамический (назначает ОС) |
| TXT Records     | `peer_name`, `version`     |

### Поиск служб

- Постоянный запрос `_p2pmsg._tcp`.
- При `NsdManager.onServiceFound` разрешить службу (получить хост и порт).
- Игнорировать свою же службу (сравнение по `deviceId`).
- При `onServiceLost` пометить пира как оффлайн.

### Ограничения на VLAN

mDNS обычно работает только в пределах link-local сети и может не проходить через VLAN без дополнительных настроек:
- VLAN должен поддерживать mDNS reflection (часто в корпоративных WiFi).
- Должен быть настроен IGMP snooping для форвардинга мультикаста.
- В таких случаях **UDP heartbeat** служит запасным вариантом.

## Протокол UDP Heartbeat

Использует UDP броадкаст для максимальной совместимости с подсетями и VLAN, которые форвардят броадкаст-трафик.

### Конфигурация сокета

```kotlin
val socket = MulticastSocket(BROADCAST_PORT).apply {
    broadcast = true
    reuseAddress = true
    timeToLive = 2  // Разрешить проход через один роутер
}
```

### Формат Heartbeat пакета

```
UDP пакет на 255.255.255.255:42000

Payload (JSON):
{
  "type": "heartbeat",
  "deviceId": "a1b2c3d4-...",
  "peerName": "Alice",
  "listenPort": 43892,
  "listenAddr": "192.168.1.42",
  "version": 1,
  "timestamp": 1717000000000,
  "pubKeyFingerprint": "sha256$..."
}
```

### Приём и обработка

1. Слушаем `0.0.0.0:42000` для UDP датаграмм.
2. Проверяем структуру JSON и `type == "heartbeat"`.
3. Игнорируем свои heartbeat (сравниваем `deviceId`).
4. Если пир новый или адрес изменился → открываем TCP соединение.
5. Если пир был помечен как оффлайн → инициируем переподключение.
6. Ведём карту "последний раз видели"; удаляем записи старше 30 секунд.

### Достижимость броадкастов

| Тип сети          | Достижимость броадкастов              |
|-------------------|---------------------------------------|
| Стандартный WiFi  | Все устройства на одной точке / подсети |
| VLAN trunk        | Все устройства в одном VLAN            |
| Корпоративный WiFi| Может быть заблокирован изоляцией AP   |
| Открытый WiFi     | Обычно работает                        |

## Комбинированный автомат состояний

```
                    ┌──────────────┐
                    │   UNKNOWN    │
                    └──────┬───────┘
                           │
              ┌────────────┼────────────┐
              │ mDNS найден│ UDP rx     │
              ▼            ▼            │
        ┌──────────┐ ┌──────────┐      │
        │ RESOLVING│ │  SEEN    │      │
        └────┬─────┘ └────┬─────┘      │
             │ resolved   │            │
             ▼            ▼            │
        ┌──────────────────────┐       │
        │     CONNECTING       │       │
        └──────────┬───────────┘       │
                   │ TCP handshake     │
                   ▼                   │
        ┌──────────────────────┐       │
        │      CONNECTED       │       │
        └──────────┬───────────┘       │
                   │ таймаут / потеря  │
                   ▼                   │
        ┌──────────────┐              │
        │   OFFLINE    │──────────────┘
        └──────────────┘  (новое обнаружение)
```
