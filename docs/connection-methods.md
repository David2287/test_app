# Методы P2P-подключения устройств на любом расстоянии

## Проблема: почему просто TCP не работает

Для соединения двух устройств в разных сетях необходимо преодолеть **NAT (Network Address Translation)** — механизм маршрутизаторов, который скрывает устройства за одним публичным IP.

```
┌──────────┐        ┌──────────┐       ┌──────────┐
│ Peer A   │        │  NAT     │       │  NAT     │   ┌──────────┐
│ 192.168.1.5│──────│ Роутер А │───────│ Роутер Б │───│ Peer B   │
└──────────┘        │ 1.2.3.4  │       │ 5.6.7.8  │   │192.168.1.10│
                    └──────────┘       └──────────┘   └──────────┘
```

Peer A не может напрямую инициировать соединение с Peer B, потому что:
- Адрес `192.168.1.10` — частный, не маршрутизируется в интернете.
- Роутер Б не знает, что входящий пакет предназначен для Peer B.
- Роутер Б блокирует входящие соединения (stateful firewall).

Далее описаны методы, решающие эту проблему для соединения на любом расстоянии.

## 1. UDP Hole Punching

### Принцип работы

Наиболее простой метод NAT-траверсала. Использует "дырку", которую NAT-роутер создаёт при исходящем UDP-пакете.

```
1. Peer A отправляет UDP пакет на публичный адрес Peer B (5.6.7.8:PORT)
   → Роутер А создаёт правило: "пакеты с 5.6.7.8:PORT пропускать к Peer A"

2. Peer B отправляет UDP пакет на публичный адрес Peer A (1.2.3.4:PORT)
   → Роутер Б создаёт правило: "пакеты с 1.2.3.4:PORT пропускать к Peer B"

3. Теперь оба роутера ожидают трафик друг от друга → P2P канал открыт
```

### На чём основан

- RFC 3027 — NAT Protocol Complications
- Используется в BitTorrent, VoIP (Skype), онлайн-играх
- Для координации требуется **третий сервер** (signal server), который сообщает пирам публичные адреса друг друга

### Преимущества
- Не требует ретрансляции данных — трафик идёт напрямую
- Нулевая стоимость серверной инфраструктуры (только лёгкий координатор)
- Очень низкая задержка

### Недостатки
- **Не работает** с симметричным NAT (Symmetric NAT)
- Не работает, если оба пира за Carrier-Grade NAT (CGNAT)
- Требует UDP-протокол (не подходит для простого TCP)

### Совместимость с медиа

UDP hole punching **идеально подходит** для видео/аудио, так как:
- Низкая задержка (UDP без retransmit)
- Можно использовать RTP поверх UDP
- Потери пакетов допустимы для real-time медиа

## 2. STUN (Session Traversal Utilities for NAT)

### Принцип работы

STUN-сервер помогает пиру узнать свой **публичный IP и порт**, которые NAT назначил для его соединения.

```
Peer A ──► STUN Server (3.3.3.3:3478)
           "С какого адреса я пришёл?"
STUN Server ──► Peer A
           "Твой публичный адрес: 1.2.3.4:54321"
Peer A использует этот адрес для hole punching
```

### На чём основан

- **RFC 8489** (обновляет RFC 5389)
- Используется в WebRTC, SIP VoIP
- Стандартный порт: 3478 (TCP/UDP)
- Лёгкий протокол — минимальная нагрузка на сервер

### Режимы

- **STUN Binding Request** — запрос на определение адреса
- **STUN Indication** — передача данных без подтверждения
- Работает поверх TCP и UDP

### Преимущества
- Очень лёгкий протокол — сервер может обслуживать миллионы клиентов
- Бесплатные публичные STUN-серверы (Google: `stun.l.google.com:19302`)
- Не участвует в передаче данных — только координация

### Недостатки
- **Не решает проблему Symmetric NAT** — STUN может определить адрес, но hole punching всё равно не сработает
- Не работает с CGNAT
- Не шифрует трафик (но это и не требуется — только координация)

## 3. TURN (Traversal Using Relays around NAT)

### Принцип работы

Когда P2P соединение невозможно (Symmetric NAT, CGNAT, firewall), TURN-сервер **ретранслирует** трафик между пирами.

```
Peer A ◄──── TURN Server ────► Peer B
              (4.4.4.4:3478)
         └──── ретрансляция ────┘
```

### На чём основан

- **RFC 8656** (обновляет RFC 5766, RFC 6156)
- Используется в WebRTC как последнее средство (fallback)
- Протокол поверх UDP, TCP, TLS

### Алгоритм

```
1. Peer A → TURN: Allocate Request
2. TURN → Peer A: Allocate Response (relayed address: 4.4.4.4:PORT)
3. Peer A → TURN: CreatePermission (Peer B)
4. Peer B → TURN: CreatePermission (Peer A)
5. Теперь оба пира могут общаться через TURN-сервер
```

### Типы ретрансляции

- **STUN-based TURN** — стандартный, UDP ретрансляция
- **TURN-TLS** — шифрованная ретрансляция поверх TLS
- **TURN-DTLS** — шифрованная ретрансляция поверх DTLS

### Преимущества
- Работает в **99.9% случаев** — самый надёжный метод
- Преодолевает любые типы NAT и firewalls
- Один сервер может обслуживать много пар пиров
- Может работать в режиме "relay only" без попытки P2P

### Недостатки
- **Высокая нагрузка на сервер** — весь трафик проходит через него
- Высокая стоимость — нужно арендовать/настроить TURN-сервер
- **Задержка удваивается** — трафик идёт через ретранслятор
- Требует пропускной способности сервера (особенно для видео/аудио)

### Стоимость для медиа

Если все звонки пойдут через TURN:
- Видео 720p: ~2-3 Mbps на звонок
- Аудио: ~64-128 kbps на звонок
- Сервер на $20/мес выдержит ~20-30 одновременных видеозвонков
- **Очень дорого** в масштабе

## 4. ICE (Interactive Connectivity Establishment)

### Принцип работы

ICE — это **фреймворк**, а не протокол. Он объединяет STUN, TURN и локальное обнаружение в единый алгоритм выбора наилучшего пути.

```
ICE собирает "кандидаты" (candidates) для каждого пира:

1. Хост-кандидаты: локальные IP (192.168.x.x)
2. Сервер-рефлексивные: публичный IP через STUN (1.2.3.4:PORT)
3. Релейные: адрес на TURN-сервере (4.4.4.4:PORT)

ICE упорядочивает их по приоритету:
   host (низкая задержка) > stun (средняя) > turn (высокая, всегда работает)
```

### Алгоритм

```
1. Каждый пир собирает все свои кандидаты (host, stun, turn)
2. Пиры обмениваются списками через сигнальный сервер
3. Каждый пир проверяет каждую пару кандидатов:
   - Peer A:host → Peer B:host
   - Peer A:host → Peer B:stun
   - Peer A:stun → Peer B:host
   - Peer A:stun → Peer B:stun
   - Peer A:turn → Peer B:turn (и так далее)
4. Первая успешная пара используется
```

### На чём основан

- **RFC 8445** (ICE), **RFC 8838** (Trickle ICE)
- Используется в WebRTC, SIP, XMPP
- **Trickle ICE** — отправка кандидатов по мере их обнаружения (быстрее)

### Преимущества
- **Самый надёжный подход** из существующих
- Автоматический выбор лучшего пути
- Адаптивен к сетевым условиям
- Де-факто стандарт в современном P2P

### Недостатки
- Сложная реализация (но есть готовые библиотеки)
- Требует STUN и TURN серверы
- Время установки соединения — до нескольких секунд (Trickle ICE быстрее)

## 5. WebRTC

### Принцип работы

WebRTC — полноценный фреймворк для P2P коммуникации, включающий:
- ICE + STUN + TURN для установки соединения
- DTLS-SRTP для шифрования
- Media streams (аудио/видео кодеки: Opus, VP8, VP9, H.264)
- Data channels (надёжная/ненадёжная передача данных)

```
┌─────────────────────────────────────┐
│             WebRTC                   │
│  ┌──────────┐  ┌──────────────────┐  │
│  │  Media   │  │   Data Channel   │  │
│  │ (VP8/H264)│  │ (SCTP over DTLS) │  │
│  └────┬─────┘  └────────┬─────────┘  │
│       │                 │            │
│  ┌────┴─────────────────┴──────────┐ │
│  │       SRTP / SCTP               │ │
│  └──────────────┬──────────────────┘ │
│                 │                    │
│  ┌──────────────┴──────────────────┐ │
│  │        ICE (STUN + TURN)        │ │
│  └──────────────┬──────────────────┘ │
│                 │                    │
│  ┌──────────────┴──────────────────┐ │
│  │    UDP / TCP / TLS              │ │
│  └─────────────────────────────────┘ │
└─────────────────────────────────────┘
```

### Компоненты для Android

- **google-webrtc** (org.webrtc:google-webrtc:1.0.+) — официальная сборка для Android
- Включает кодеки, ICE, медиа-пайплайн
- Нативная библиотека через JNI

### Настройка сигналинга

Сигнальный сервер (для обмена SDP, ICE кандидатами) реализуется отдельно:
- WebSocket сервер
- REST API
- Firebase Cloud Messaging (FCM)

```
Peer A                    Сигнальный сервер                    Peer B
  │                             │                                │
  │───── SDP Offer (WebSocket) ──►                              │
  │                             │───── SDP Offer ─────────────────►
  │                             │◄──── SDP Answer ────────────────│
  │◄──── SDP Answer (WS) ────────│                                │
  │───── ICE Candidates ────────►──── ICE Candidates ────────────►│
  │◄──── ICE Candidates ────────◄──── ICE Candidates ─────────────│
  │                                                               │
  │◄══════════ WebRTC P2P Channel (медиа + данные) ═══════════►  │
```

### Преимущества
- **Всё в одном**: медиа + данные + NAT traversal
- Готовые кодеки для видео (VP8/VP9/H264) и аудио (Opus)
- Встроенное шифрование (DTLS-SRTP — обязательное)
- Data Channel для текстовых сообщений (может работать без медиа)
- Активное сообщество и поддержка Google
- Кроссплатформенность

### Недостатки
- Требует сигнальный сервер (но он минимальный — только метаданные)
- Библиотека google-webrtc ~30 MB
- Сложный API (много boilerplate кода)
- Сборка мусора на нативном уровне

## 6. DHT (Distributed Hash Table) — Kademlia

### Принцип работы

Децентрализованный поиск пиров без единого сервера. Каждый пир хранит часть глобальной таблицы "ключ → контакт".

```
Kademlia:
- Каждый пир имеет 160-битный ID
- Пир хранит контакты ближайших (по XOR) к его ID пиров
- Поиск пира: O(log n) шагов, где n — количество пиров в сети
- Устойчив к выбыванию пиров
```

### Использование для обнаружения

```
1. Пир присоединяется к DHT-сети (знает хотя бы один bootstrap узел)
2. Регистрирует свои сервисы (чат, медиа)
3. Другие пиры находят его через DHT-запрос к ключу
4. После нахождения — прямой ICE-STUN-TURN коннект
```

### На чём основан

- **Kademlia** (Petar Maymounkov, David Mazières, 2002)
- Используется в BitTorrent (Mainline DHT), IPFS, Ethereum
- **libp2p Kademlia** — реализация на Go/JS/Rust/Python

### Преимущества
- Полностью децентрализованное обнаружение
- Нет единой точки отказа
- Не требует сервера для координации
- Работает даже при частичном отключении сети

### Недостатки
- Сложность реализации
- Время поиска ~1-10 секунд
- Не решает проблему NAT сам по себе — нужен ICE/STUN/TURN
- Высокий расход батареи (постоянное поддержание таблицы)

## 7. libp2p

### Принцип работы

libp2p — модульный стек сетевых протоколов для P2P. Предоставляет:
- NAT traversal (NAT Manager, AutoNAT, Hole Punching)
- Мультиплексирование (mplex, yamux)
- Шифрование (TLS, Noise)
- Обнаружение (mDNS, DHT, rendezvous)
- Транспорты (TCP, UDP, QUIC, WebSockets)

```
libp2p node
  ┌──────────────────────────────────────┐
  │  Peer Identity (PeerID = hash(pubkey))│
  ├──────────────────────────────────────┤
  │  Transport Manager                   │
  │  ┌──────┐ ┌──────┐ ┌──────────────┐│
  │  │ TCP  │ │ QUIC │ │ WebSocket    ││
  │  └──────┘ └──────┘ └──────────────┘│
  ├──────────────────────────────────────┤
  │  NAT Traversal                       │
  │  ┌────────┐ ┌─────────┐ ┌──────────┐│
  │  │AutoNAT │ │HolePunch│ │ Relay    ││
  │  └────────┘ └─────────┘ └──────────┘│
  ├──────────────────────────────────────┤
  │  Discovery                           │
  │  ┌──────┐ ┌─────────┐ ┌──────────┐  │
  │  │mDNS  │ │Kademlia │ │Rendezvous│  │
  │  └──────┘ └─────────┘ └──────────┘  │
  ├──────────────────────────────────────┤
  │  Stream Mux                          │
  │  ┌──────┐ ┌──────────┐              │
  │  │mplex │ │  yamux   │              │
  │  └──────┘ └──────────┘              │
  └──────────────────────────────────────┘
```

### На чём основан

- Проект Protocol Labs (авторы IPFS, Filecoin)
- Мультиплатформенный: Go, JS, Rust, Python, Nim
- Kotlin/JVM версия: **JVM-libp2p**

### Преимущества
- Максимальная гибкость — можно собрать свою конфигурацию
- Встроенный NAT traversal (AutoNAT, relay, hole punch)
- Не требует отдельного сигнального сервера
- Модульный — берите только нужное

### Недостатки
- **Сложность** — очень много концепций для изучения
- JVM-libp2p всё ещё развивается, может быть нестабильна
- Нет встроенной поддержки медиа-стриминга (нужен WebRTC поверх)
- Избыточен, если нужно просто обмениваться сообщениями
- Большой размер APK

## 8. Tor Onion Services (скрытые сервисы)

### Принцип работы

Каждый пир создаёт "луковый сервис" — доступный через сеть Tor, без знания реального IP.

```
Peer A ───┬─── Tor Network ───┬─── Peer B
          │                   │
      ┌────┴────┐        ┌────┴────┐
      │ Introduction   │ Rendezvous │
      │ Point          │ Point      │
      └─────────┘      └─────────┘
      
Каждый пир доступен по адресу: xyz123456.onion:PORT
```

### Преимущества
- Абсолютная анонимность
- Работает из-за любых NAT и фаерволлов
- Не требует серверов

### Недостатки
- **Огромная задержка** — непригодно для видео/аудио
- Низкая пропускная способность
- Установка соединения ~10-30 секунд
- Потребление батареи
- Tor заблокирован в некоторых странах

## 9. QUIC (Quick UDP Internet Connections)

### Принцип работы

Протокол от Google поверх UDP с мультиплексированием и встроенным шифрованием. Может быть использован как транспорт для P2P.

- Основан на UDP — обходит многие NAT
- Встроенное шифрование (TLS 1.3)
- 0-RTT handshake для повторных соединений
- Мультиплексирование без head-of-line blocking

### На чём основан

- **RFC 9000** (QUIC), **RFC 9001** (TLS over QUIC)
- HTTP/3 использует QUIC
- Реализации: Cronet (Google), quiche (Cloudflare), MsQuic (Microsoft)

### Применение для P2P

- QUIC может быть транспортом в libp2p
- WebRTC поверх QUIC (исследуется)
- Быстрое переподключение при смене сети (connection migration)

### Преимущества
- Быстрый handshake (0-RTT)
- Connection migration — переключение между WiFi/мобильными сетями без разрыва
- Встроенное шифрование
- Хорошая производительность

### Недостатки
- Относительно новый — не везде поддерживается
- На Android — через Cronet, не нативно
- NAT traversal не решён полностью

## Рекомендация для вашего приложения

### Основной выбор: WebRTC + ICE/STUN/TURN

WebRTC — **единственный метод**, который покрывает все требования:

| Требование | Как WebRTC решает |
|------------|-------------------|
| Любое расстояние | ICE + STUN + TURN — работает через NAT, CGNAT, firewalls |
| Текстовые сообщения | DataChannel (SCTP over DTLS) — надёжная доставка |
| Видео в будущем | Встроенные кодеки (VP8, VP9, H.264) + адаптивный битрейт |
| Аудио в будущем | Opus кодек (адаптивный, от 6 до 510 kbps) |
| Стабильность | Автоматический выбор кандидата, fallback на TURN |
| Шифрование | DTLS-SRTP (обязательное, встроенное) |

### Архитектура с WebRTC

```
┌─────────────────────────────────────────────┐
│              Signal Server                   │
│          (WebSocket / REST)                  │
│  ┌──────────┐  ┌───────────────────────┐    │
│  │Обмен SDP │  │ Обмен ICE кандидатами │    │
│  └──────────┘  └───────────────────────┘    │
└────────────────────┬────────────────────────┘
                     │ (только метаданные)
                     │
    ┌────────────────┴────────────────┐
    │              Internet            │
    │  ┌──────────┐     ┌──────────┐  │
```

### Конфигурация ICE для вашего приложения

```kotlin
val iceServers = listOf(

        .createIceServer(),

    PeerConnection.IceServer.builder("stun:stun1.l.google.com:19302")
        .createIceServer(),
    
    // TURN (если нужно — для Symmetric NAT / CGNAT)
    PeerConnection.IceServer.builder("turn:turn.example.com:3478")
        .setUsername("user")
        .setPassword("password")
        .createIceServer()
)

// Создание конфигурации
val config = PeerConnection.RTCConfiguration(iceServers).apply {
    // Приоритет: P2P > STUN > TURN

    // Bundle аудио и видео в один ICE транспорт

    // Использовать DTLS для шифрования
    sdpSemantics = SdpSemantics.UNIFIED_PLAN
```

### Когда использовать TURN (важно для медиа)

Используйте TURN **только когда ICE не может установить P2P**:

```
IceConnectionState:
  CHECKING → CONNECTED (P2P через STUN/хост)  ← лучший сценарий
  CHECKING → CONNECTED (через TURN)           ← худший сценарий
  
Статистика ICE соединения:
  - candidatePair (typ host)    → задержка ~0-5ms   ← идеально
  - candidatePair (typ srflx)  → задержка ~5-50ms  ← хорошо
  - candidatePair (typ relay)  → задержка ~50-200ms ← терпимо
```

Рекомендуется предоставлять TURN только для **процента случаев, где P2P невозможен**:


## Альтернативные варианты (если WebRTC по каким-то причинам не подходит)

### Вариант A: ICE + STUN + TURN (без WebRTC)

Используя **libjuice** (библиотека ICE на C с Kotlin/Native) или **ice4j** (JVM). Даёт полный контроль, но требует ручной реализации медиа-кодеков.

- **Плюсы:** Меньше размер APK, полный контроль
- **Минусы:** Нужно реализовать аудио/видео самостоятельно (через MediaCodec + RTP)

### Вариант B: libp2p для обнаружения + WebRTC для медиа

- **Плюсы:** Серверное обнаружение пиров (DHT), децентрализация
- **Минусы:** Сложность, JVM-libp2p нестабильна на Android

### Вариант C: Только QUIC

Cronet (Google) для Android поддерживает QUIC, можно реализовать P2P поверх QUIC. Но NAT traversal не решён встроенными средствами.

## Заключение: что использовать для вашего приложения

| Этап | Рекомендация |
|------|-------------|
| **Текст сейчас** | WebRTC + **только DataChannel** (без медиа). ICE = STUN (Google бесплатно) + опциональный TURN. |
| **Аудио/видео потом** | WebRTC уже включает всё — просто добавить MediaStream. **Без переписывания кода.** |
| **Обнаружение пиров на расстоянии** | Сигнальный сервер (WebSocket) — лёгкий, только для обмена SDP/ICE. |
| **Обнаружение в локальной сети** | mDNS (Android NSD) + UDP heartbeat — как описано в p2p-discovery.md. |
| **Надёжность доставки** | DataChannel в режиме ordered + самодельные ACK (как в protocol.md). |
| **Безопасность** | DTLS-SRTP (WebRTC) поверх самоподписанных сертификатов + TOFU. |

### Почему именно WebRTC

1. **Единый протокол для текста, аудио, видео** — не нужно переписывать коммуникационный слой при добавлении медиа.
2. **Готовая библиотека для Android** — `org.webrtc:google-webrtc`.
3. **Лучший NAT traversal** — ICE + STUN + TURN с автоматическим fallback.
4. **Адаптивный битрейт** — кодек подстроится под сетевые условия.
5. **Производственное использование** — Zoom, Google Meet, Discord, Telegram — все используют WebRTC.
