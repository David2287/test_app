# Спецификация проводного протокола

## Обзор

Протокол — лёгкий бинарный фрейминг с JSON-нагрузкой поверх TCP. Каждый пир запускает TCP-сервер для входящих сообщений и поддерживает TCP-клиентские соединения для исходящих.

## Фрейминг

Каждое сообщение в канале использует **фрейминг с префиксом длины**:

```
┌───────────────────────────────────────────────┐
│ 4 байта  │        1 байт     │   Переменная   │
│  Length  │   Message Type    │    Payload     │
│ (big-endian) │                │   (JSON/raw)   │
└──────────────┴────────────────┴───────────────┘
```

- **Length (uint32, big-endian):** общее количество байт фрейма *без учёта* этих 4 байт.
- **Message Type (uint8):** идентификатор типа (см. ниже).
- **Payload:** содержимое зависит от типа сообщения.

## Типы сообщений

| Код  | Имя             | Формат нагрузки | Описание                        |
|------|-----------------|-----------------|---------------------------------|
| 0x01 | HANDSHAKE       | JSON            | Начальное рукопожатие           |
| 0x02 | HANDSHAKE_ACK   | JSON            | Подтверждение рукопожатия       |
| 0x03 | TEXT            | JSON            | Текстовое сообщение чата        |
| 0x04 | ACK             | JSON            | Квитанция доставки              |
| 0x05 | PING            | пусто           | Keepalive ping                  |
| 0x06 | PONG            | пусто           | Keepalive ответ                 |
| 0x07 | FILE_META       | JSON            | Метаданные передачи файла       |
| 0x08 | FILE_CHUNK      | бинарный        | Чанк данных файла               |
| 0x09 | BYE             | пусто           | Корректное отключение           |

## Определения сообщений

### Handshake (0x01)

Отправляется сразу после установки TCP-соединения.

```json
{
  "protocolVersion": 1,
  "deviceId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "peerName": "Alice",
  "pubKey": "base64-encoded-public-key",
  "timestamp": 1717000000000
}
```

### Handshake ACK (0x02)

```json
{
  "protocolVersion": 1,
  "deviceId": "b2c3d4e5-f6a7-8901-bcde-f12345678901",
  "peerName": "Bob",
  "pubKey": "base64-encoded-public-key",
  "accepted": true,
  "rejectReason": null
}
```

### Текстовое сообщение (0x03)

```json
{
  "messageId": "msg_abc123",
  "senderId": "a1b2c3d4-...",
  "recipientId": "b2c3d4e5-...",
  "conversationId": "conv_001",
  "text": "Привет, Боб!",
  "timestamp": 1717000010000,
  "replyTo": null
}
```

### Квитанция доставки (0x04)

```json
{
  "messageId": "msg_abc123",
  "status": "received"
}
```

Значения status: `received`, `read`.

### Метаданные файла (0x07)

```json
{
  "messageId": "msg_file_001",
  "fileName": "photo.jpg",
  "fileSize": 2048576,
  "fileHash": "sha256:abc123...",
  "chunkSize": 65536,
  "totalChunks": 32
}
```

Затем следуют фреймы `FILE_CHUNK`.

### Чанк файла (0x08)

Нагрузка — сырые бинарные данные. Заголовок на чанк отсутствует; сборка использует `chunkSize` и порядковый номер из `FILE_META`.

### Keepalive (0x05 / 0x06)

Пустая нагрузка. Пир обязан ответить на `PING` сообщением `PONG` в течение 10 секунд, иначе соединение закрывается.

## Жизненный цикл соединения

```
TCP подключён
      │
      ▼
Отправка HANDSHAKE ─────────► Ожидание HANDSHAKE_ACK
      │                              │
      │                         ┌────┴────┐
      │                         │         │
      │                    принято    отклонено
      │                         │         │
      │                         ▼         ▼
      │                      READY     CLOSE
      │
      ▼
    Состояние READY
  ┌──────────────────┐
  │  ↔ TEXT/ACK      │
  │  ↔ FILE_META/    │
  │     FILE_CHUNK   │
  │  ↔ PING/PONG     │
  └──────────────────┘
      │
      ▼
Отправка BYE ──► CLOSE
```

## Порядок сообщений и надёжность

- **Порядок:** Сообщения доставляются по порядку в рамках одного TCP-соединения. Прикладной слой использует `messageId` для идемпотентности.
- **Надёжность:** Отправитель ждёт фрейм `ACK`. Если ACK не получен в течение 30 секунд, сообщение помещается в очередь повтора.
- **Оффлайн-очередь:** Сообщения для оффлайн-пиров хранятся в Room и отправляются при следующем подключении.

## Адресация

Пиры идентифицируются **UUID v4** (`deviceId`). Этот ID:
- Генерируется при первом запуске и хранится в `SharedPreferences`.
- Стабилен между перезагрузками.
- Используется как первичный ключ в списке пиров (roster).

Центрального реестра или сервера имён не существует.
